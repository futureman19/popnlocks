## Observed behavior

- Both independent Node children reached ready latches before release. Each called the actual CLI startup against one fresh state directory. The owner kept its lock through the competing open. The loser returned `EEXIST` before server admission, chain reads, or signer invocation. This held for identical and distinct quote IDs sharing one synthetic coin.
- In each race the owner appended one hold and called the inert signer once. Its deliberate failure left the hold in place. On orderly exit the lock was released. A fresh process replaying the same quote returned `RESERVED` before **any** chain read; a different quote for the same coin returned `NO_SIZED_COIN`. Neither retry signed or changed the hold.
- A prior-day hold stayed unchanged on replay. A pre-existing stop file prevented chain reads, reservation and signing. Forced process death immediately after the real reservation returned left one hold, no signer call and a persistent lock. A fresh process was refused; no stale-lock removal was attempted.
- No double reservation, duplicate signer invocation, or erased hold was observed. The lock result checked is the error **code** at the CLI `main()` boundary. The probe records only bounded labels. The executable wrapper logs `error.message`, not a normalized code: operator stderr can include a filesystem path. This is not evidence of sanitized executable stderr or HTTP error behavior.

## Limits

Local Windows filesystem and compliant CLI entrants only. This tests process death, not power loss, remote storage or operator intervention. The child replaces external chain, signer and server factories; it captures the real maker after lock acquisition rather than listening on a port. No signature is produced. No operational keys, funds, live providers, broadcasts, pushes, deployments or release approval.
